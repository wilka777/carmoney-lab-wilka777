# D2.1.1: замер токенов для поиска по пробегу

Трек: разработчик. Вопрос: «Все места, где используются `mileage` и
`max_mileage_km`: файл и функция».

| Замер | Input tokens | Output tokens | Стоимость, $ | Агент звал ast-index |
| --- | ---: | ---: | ---: | --- |
| Без индекса | 52 499 | 2 228 | 0.00984231 | нет |
| ast-index | 55 236 | 2 775 | 0.00755088 | да |
| ast-index + Caveman | 47 765 | 1 764 | 0.00837823 | да |
| Итог 2.1.4: выбор инструментов | 334 548 | 3 677 | 0.03969300 | да |

## Команды индекса

- `ast-index search mileage`
- `ast-index search max_mileage_km`

## Вывод

При прямом указании использовать `ast-index` агент вызвал индекс, а не
`grep`. Стоимость ответа снизилась с $0.00984231 до $0.00755088, хотя
входных токенов стало немного больше. Сам по себе установленный индекс не
меняет поведение модели: использование потребовало явного указания в
промпте.

Caveman сохранил тот же набор из 5 symbols, первые 20 content matches,
все 3 совпадения `max_mileage_km` и обе команды `ast-index`; ничего из
ответа индекса не потерялось. По сравнению с `ast-index` без Caveman он
сэкономил 7 471 input и 1 011 output tokens, всего 8 482 tokens. При этом
стоимость по Activity выросла на $0.00082735, поэтому экономия токенов в
этом запуске не дала экономии в долларах.

Итоговый замер 2.1.4 объединяет два финальных запуска выбора инструментов
и повторную UI-проверку. В сравнении со строкой «Без индекса» он больше на
283 498 tokens и на $0.02985069: Playwright-исполнение требует заметно
больше контекста и действий, чем один вопрос поиска по коду.
