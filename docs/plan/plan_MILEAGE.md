# План MILEAGE: правило по пробегу

Основание: `docs/spec/spec_MILEAGE.md` и `docs/intent/intent_MILEAGE.md`.
Правило по пробегу понижает только потенциальный `approve` до `review`; `reject`
по LTV остаётся `reject`.

## 1. Файлы

- `backend/config/rules.php` — добавить отдельный порог решения 400000 рядом с
  текущим валидационным максимумом; существующий максимум 500000 не менять.
- `backend/src/Domain/DecisionEngine.php` — учитывать пробег при выборе решения,
  сохранив приоритет `reject` по LTV.
- `backend/src/Domain/AssessmentService.php` — передать валидированный пробег в
  расчёт решения.
- `backend/src/AppFactory.php` — передать в расчёт порог пробега из правил.
- `tests/Unit/DecisionEngineTest.php` — покрыть приоритет решения и границы
  пробега.
- `tests/Unit/AssessmentServiceTest.php` — покрыть сквозные решения и лимит.
- `tests/Unit/ApplicationValidatorTest.php` — закрепить неизменность границы
  валидации и поведение отсутствующего пробега.

## 2. Шаги

1. Написать тесты для 399999, 400000, 400001, высокого LTV с 400001 и
   отсутствующего пробега; убедиться, что новые сценарии падают до изменения
   рабочего кода.
2. Добавить конфигурируемый порог решения по пробегу, не изменяя существующий
   валидационный максимум.
3. В расчёте решения сначала сохранить `reject` для LTV выше текущей границы,
   затем понизить до `review` только оставшийся потенциальный `approve` при
   превышении порога пробега; существующие LTV-границы не менять.
4. Передать валидированный пробег и конфигурацию в расчёт решения через текущую
   сборку приложения.
5. Запустить unit-тесты и lint; выполнить e2e-проверку: пробег 400001 даёт
   `review`.

## 3. Тесты

- 399999 при LTV 50.0 → `approve`.
- 400000 при LTV 50.0 → `approve`.
- 400001 при LTV 50.0 → `review`, лимит 0.
- 400001 при LTV 95.0 → `reject`.
- Отсутствующий пробег → `ValidationException`, решения нет.
- 500001 → `ValidationException`, а не `review`.
- Существующие LTV-сценарии с пробегом ниже порога сохраняют текущие решения.

## 4. Риски

- Если заменить текущую границу валидации 500000 на 400000, диапазон
  400001–500000 станет ошибкой вместо `review`; оба порога нужны одновременно.
- Проверка пробега до проверки LTV может ошибочно смягчить `reject`; порядок
  проверок обязан сохранять `reject`.
- Изменение входа расчёта решения требует обновить все прямые вызовы в
  приложении и unit-тестах одновременно.
- Не входят: текущие границы LTV, фронтенд, API, база, сиды, возрастной лимит
  и новые причины решения.

## Вопросы

- Бизнес-обоснование порога 400000 перенесено риск-менеджменту; оно не блокирует
  реализацию явно поставленного учебного правила.
