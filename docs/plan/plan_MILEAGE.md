# План MILEAGE: пробег не больше 400 000 км, иначе решение `review`

Задача `MILEAGE` (день 1, `docs/README.md`). Правило: пробег авто больше
400 000 км — решение по заявке `review`; пробег не больше 400 000 км — решение
считается по LTV, как сейчас. Заявка с пробегом 400001 остаётся валидной и
обязана получить `review`, а не ошибку валидации (`code_map.md:44`).

Основания: постановка задачи; `docs/setup/code_map.md` (строки 42–105 — место
правила и чего не хватает); разведка по `mileage` (`docs/setup/agents.md` и
проверка файлов planner'ом, 2026-09-24). Спека `spec_MILEAGE.md` ещё не создана:
в ДЗ.1 план сверяется с ней и дополняется (`docs/plan/README.md:18`).

Текущее состояние: пробег валидируется в `ApplicationValidator` (0…500 000,
`rules.php:23`), нормализуется в `$input['mileage']`
(`ApplicationValidator.php:78`), но в решение не попадает:
`DecisionEngine::decide(float $ltv)` принимает только LTV
(`DecisionEngine.php:30`), и `AssessmentService` пробег дальше не передаёт
(`AssessmentService.php:33`).

## 4. Риски

1. Существующая проверка `max_mileage_km = 500000` (`ApplicationValidator.php:44-45`, `rules.php:23`) — главный риск: если «упростить» и снизить `max_mileage_km` до 400000, пробег 400001+ начнёт давать HTTP 422 `ValidationException` вместо `review` — требование нарушится, диапазон 400001–500000 выпадет. Оба порога нужны одновременно: 500000 — граница валидности заявки, 400000 — граница решения. Тесты в `ApplicationValidatorTest` это закрепляют.
2. Пробег выше 500000 до `DecisionEngine` не доходит (422 на валидации): новое правило действует только в диапазоне 400001–500000; тест на 400001 лежит внутри него.
3. Смягчение reject: проверка пробега до LTV-веток (`code_map.md:52–56`) превращает reject в review при высоком пробеге и высоком LTV — это ослабление риск-решения. Альтернатива — проверять пробег только после approve-ветки, тогда reject сохраняется. Выбор приоритета — решение риск-менеджмента (Вопрос 1).
4. Смена сигнатуры `decide()` ломает все прямые вызовы: в репозитории это `AssessmentService.php:33`, `AppFactory.php:37` и оба тестовых файла (`setUp` и провайдер `DecisionEngineTest`). Обновлять обязательно одним коммитом, иначе `ArgumentCountError` уронит весь набор.
5. Существующие LTV-тесты `DecisionEngineTest` вызывают `decide($ltv)` одним аргументом — провайдер обязан передавать и пробег, иначе набор красный по технической причине, а не по бизнесовой.
6. Граница LTV 60.0: комментарий `rules.php:39` обещает approve при `LTV <= approve_max`, код (`DecisionEngine.php:32`, строго `<`) даёт review при ровно 60.0. Существующее расхождение; в MILEAGE не трогаем — иначе молча изменится решение на границе (риск-менеджмент, Вопрос 4).
7. `approved_limit`: при принудительном review лимит автоматически 0 (`AssessmentService.php:39`) — код лимита менять не нужно, «улучшать» его попутно нельзя.
8. Фронтенд: пустое поле пробега уходит как 0 (`Number('')`, `frontend/app.js:13–15`) — с формы «пустой пробег» проходит как 0 км, а из API без ключа — 422. Правило MILEAGE это несоответствие не чинит (не входит).
9. Сиды `db/seed.sql`: максимальный пробег 296000 — все ниже 400000, решения в сиде не меняются, `make seed` пересчитывать не нужно.

Не входит в задачу:

- `ApplicationValidator`, значение `max_mileage_km`, тексты ошибок валидации
- фронтенд (отображение `review` уже есть, `styles.css:72–75`), `db/` (схема, сиды), репозиторий и HTTP-слой
- расчёт `approved_limit` (правило «сумма только при approve» не меняется)
- граница LTV 60.0 и комментарий `rules.php:39`
- `tests/Feature/`, `scripts/`, `.githooks/`

## Вопросы, на которые без заказчика не ответить

1. Приоритет над reject: при LTV 95 (reject) и пробеге 400001 решение должно быть `review` (как выбрано в `code_map.md:52–56` и в этом плане) или reject остаётся reject? Смягчать отказ из-за пробега — решение риск-менеджмента.
2. «Пустой пробег»: какое поведение ожидается при отсутствии или пустом значении пробега? Сейчас: ключа нет — 422 «Пробег от 0 до 500000 км»; пустая строка или 0 — приводится к 0 и проходит как 0 км. Ждать `review` при неизвестном пробеге или оставить ошибкой валидации?
3. Поведение выше 500000: пробег 500001+ остаётся ошибкой валидации (422), а не `review`/`reject` — подтвердить, что порог 400000 не должен заменить или снизить `max_mileage_km`.
4. Существующая граница LTV 60.0 (комментарий `rules.php:39` расходится с кодом): чинить отдельной задачей (approve при `<= 60.0`) или оставить как есть? В рамках MILEAGE менять нельзя — это чужое решение риск-менеджмента.
